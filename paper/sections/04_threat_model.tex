\section{Threat Taxonomy}
\label{sec:threat_model}

We model EIP-7702 vulnerabilities as \textit{sandbox boundary violations}. Each boundary represents a pre-7702 security assumption that developers encode into Solidity contracts. EIP-7702 delegation invalidates these assumptions, creating exploitable gaps.

\subsection{Check Classification}

Each of the 30 checks follows a uniform structure:

\begin{enumerate}
    \item \textbf{Pattern}: The source-level code pattern that encodes the broken assumption (e.g., \texttt{require(tx.origin == msg.sender)}).
    \item \textbf{Boundary}: Which of the 8 sandbox boundaries is violated.
    \item \textbf{Bypass class}: The attack primitive enabled (e.g., \textit{delegation\_code\_execution}, \textit{storage\_corruption}).
    \item \textbf{Severity}: CRITICAL (7 checks), HIGH (9), or MEDIUM (5) for delegation checks; HIGH (9) for validation checks, based on exploitability and impact.
    \item \textbf{CWE}: Standard weakness classification for interoperability.
\end{enumerate}

Severity distribution reflects real-world impact: CRITICAL checks (AA7702-001, 002, 007, 008, 009, 010, 016---7 checks) represent patterns where exploitation leads to direct fund loss or account takeover. HIGH checks require specific preconditions (delegation to a malicious target). MEDIUM checks identify defense-in-depth issues.

\subsection{ERC-7562 Validation Scope Rules}

In addition to the 21 delegation checks, ChainEDR implements 9 checks for ERC-7562~\cite{erc7562} validation scope rules (AA7562-001 through AA7562-009). These rules target account abstraction validation functions (\texttt{validateUserOp}, \texttt{validatePaymasterUserOp}) and bundler logic:

\begin{itemize}
    \item \textbf{AA7562-001}: Validation reads blocked environment opcodes (ORIGIN, TIMESTAMP, COINBASE, etc.)
    \item \textbf{AA7562-002}: Validation performs value transfers (violates OP-061)
    \item \textbf{AA7562-003}: Validation depends on mutable external code identity (COD-010)
    \item \textbf{AA7562-004}: Bundler accepts multiple authorization tuples (AUTH-010)
    \item \textbf{AA7562-005}: Delegated account used outside sender role (AUTH-020/030)
    \item \textbf{AA7562-006}: Same-sender operations with inconsistent delegates (AUTH-040)
    \item \textbf{AA7562-007}: Signature validation omits userOpHash binding
    \item \textbf{AA7562-008}: Validation callable without EntryPoint gate
    \item \textbf{AA7562-009}: preVerificationGas omits EIP-7702 PER\_EMPTY\_ACCOUNT\_COST
\end{itemize}

These rules are critical for EIP-7702-delegated accounts operating within the ERC-4337 pipeline, where bundler-side validation divergence can lead to griefing or censorship attacks.

\subsection{PreBehaviorTrace Model}

For each finding, ChainEDR generates a \textit{PreBehaviorTrace}---a structured evidence record that captures the causal chain:

\begin{enumerate}
    \item \textbf{Assumptions detected}: What the code assumes (e.g., ``caller cannot execute code'').
    \item \textbf{Delegated behavior possible}: What a delegated EOA can now do (e.g., ``execute arbitrary callback logic'').
    \item \textbf{Violated boundary}: Which sandbox boundary is broken.
    \item \textbf{Evidence}: Source location, matched pattern, confidence score.
\end{enumerate}

This model distinguishes ChainEDR from generic pattern matchers: each finding includes a structured explanation of \textit{why} the pattern is vulnerable specifically because of EIP-7702, not just that a suspicious pattern exists.
